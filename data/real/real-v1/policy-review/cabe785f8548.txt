The <a href="https://aws.amazon.com/cli/">AWS Command Line Interface (AWS CLI)</a>, the <a href="https://aws.amazon.com/developer/tools/">AWS SDKs</a>, and your coding agents speak to it over a local HTTPS endpoint using the same AWS APIs they would use in the cloud, from your laptop. AWS Emulator has no additional service fee. You pay only for AWS resources when you deploy on AWS. Its source is on <a href="https://github.com/aws/aws-emulator">GitHub</a>. You install it from an RPM or Debian package on Linux, and on macOS and Windows you run it in Docker.</p> 
<p><span id="more-106044"></span></p> 
<p><strong>How it works</strong><br> You install the emulator, start it, and point your tools at the local endpoint. When AWS Emulator starts, it generates its own credentials, a config file, and a certificate, and writes them to <code>~/.aws/emulator/9297/</code>. You set environment variables so the AWS SDK talks to your laptop instead of AWS, and your application code stays unchanged.</p> 
<p>From there, your existing tests, CLI scripts, and coding agents keep working the way they already do. A unit test that creates an <a href="https://aws.amazon.com/dynamodb/">Amazon DynamoDB</a> table, writes an item, and reads it back is the same test, and it runs on your machine without a deployment. A coding agent can create resources, check the result, and iterate again without waiting on a deployment in a Region.</p> 
<p>The emulator is implemented in Rust so that it stays light on CPU and memory on a laptop. It supports the APIs of AWS services that have an API model in the AWS API models repository on GitHub, and because it’s built from those models, the same ones the AWS SDKs use, your requests and the errors you get back have the same shape as on AWS.</p> 
<p>If you are a developer, especially one working with coding agents such as Kiro or Claude Code, you can use that loop to test AWS interactions of real complexity locally.</p> 
<p><strong>Let’s try it out</strong><br> To get started, I installed the package on <a href="https://aws.amazon.com/linux/amazon-linux-2023/">Amazon Linux 2023</a>. The package adds the <code>aws-emulator</code> command to <code>/usr/bin/</code>, so it’s on the path.</p> 
<pre class="lang:sh decode:true">PKG=https://downloads.aws.com/aws-emulator/packages/aws-emulator/LTS/latest
sudo dnf install -y $PKG/aws-emulator-x86_64.rpm

aws-emulator -v</pre> 
<p>On macOS and Windows, you build a Docker image from the short Dockerfile in the documentation and run the emulator in a container. We don’t publish a ready-made image.</p> 
<p>I started the emulator with <code>aws-emulator</code>. It serves HTTPS on <code>127.0.0.1:9297</code>, so only my own computer can reach it, and it writes its log as JSON lines that show the address, the config file, and the certificate file.</p> 
<pre class="lang:sh decode:true">aws-emulator</pre> 
<p>In another terminal, I set the environment variables that point the AWS CLI at the emulator, and unset any variables that could supply real AWS credentials.</p> 
<pre class="lang:sh decode:true">export AWS_ENDPOINT_URL=https://127.0.0.1:9297
export AWS_SHARED_CREDENTIALS_FILE=~/.aws/emulator/9297/emulator_credentials
export AWS_CONFIG_FILE=~/.aws/emulator/9297/config
export AWS_EC2_METADATA_DISABLED=true
export AWS_DISABLE_HOST_PREFIX_INJECTION=true
export AWS_REGION=us-east-1
export AWS_DEFAULT_REGION=us-east-1
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN AWS_PROFILE</pre> 
<p>The emulator generates new keys each time it starts. Its access key IDs start with <code>EMULATOR</code>, so you can’t mistake them for real AWS keys, and it rejects requests signed with any other keys. To confirm that my shell was talking to the emulator, I checked the health endpoint and the caller identity. The emulator uses a single account, <code>000000000000</code>.</p> 
<pre class="lang:sh decode:true">curl --cacert ~/.aws/emulator/9297/ca.pem https://127.0.0.1:9297/__admin/health

aws sts get-caller-identity</pre> 
<p>Then I created a bucket, copied in a small object, and listed it.</p> 
<pre class="lang:sh decode:true">$ aws s3 mb s3://local-getting-started
make_bucket: local-getting-started

$ echo "hello from the emulator" &gt; hello.txt

$ aws s3 cp hello.txt s3://local-getting-started/
upload: ./hello.txt to s3://local-getting-started/hello.txt

$ aws s3 ls s3://local-getting-started/</pre> 
<p>With the AWS CLI pointed at my laptop, I had the same commands I already use and a local endpoint that answered them.</p> 
<p>Next I wanted to see it the way I actually work now, so with the emulator still running I opened <a href="https://kiro.dev/">Kiro</a> and asked it to create an Amazon DynamoDB table, write an item, and read it back, all against AWS Emulator rather than my AWS account.</p> 
<pre class="lang:sh decode:true">kiro&gt; Using the local AWS Emulator (the environment variables
      are already set in this shell), create a DynamoDB table
      "kiro-demo" with a string key "id", put an item
      {id: "item-1", msg: "hello from kiro"}, then read it
      back with get-item.

$ aws dynamodb create-table --table-name kiro-demo \
    --attribute-definitions AttributeName=id,AttributeType=S \
    --key-schema AttributeName=id,KeyType=HASH \
    --billing-mode PAY_PER_REQUEST

$ aws dynamodb put-item --table-name kiro-demo \
    --item '{"id": {"S": "item-1"}, "msg": {"S": "hello from kiro"}}'

$ aws dynamodb get-item --table-name kiro-demo --key '{"id": {"S": "item-1"}}'</pre> 
<p>To use the same setup with an existing test suite, I would start the emulator, set the same environment variables in the script that runs the tests, and run them as usual.</p> 
<p><strong>Using the emulator in process</strong><br> Running the emulator as a local process gives you an HTTPS endpoint that works with the AWS CLI and the AWS SDKs through environment variables. Some SDKs need an extra setting to trust the emulator certificate, for example a trust store for the <a href="https://aws.amazon.com/sdk-for-java/">AWS SDK for Java</a>. For tests, there is a second option. AWS Emulator ships an embedded mode that you instantiate directly inside your test process and wire into the SDK through its HTTP client, rather than talking to a separate server over the network. Each embedded instance keeps its own state, so tests do not share buckets, tables, or queues, and you can run many of them in parallel. Embedded mode is available for the <a href="https://aws.amazon.com/sdk-for-rust/">AWS SDK for Rust</a>. You add the <code>aws-emulator-embedded</code> crate from GitHub to the <code>[dev-dependencies]</code> section of your <code>Cargo.toml</code> file. The following example creates an Amazon DynamoDB table, writes an item, and reads it back, entirely in process.</p> 
<pre class="lang:rust decode:true"><code>use aws_emulator_embedded::{AwsEmulatorEmbedded, EmbeddedOptions};
use aws_sdk_dynamodb::types::{
    AttributeDefinition, AttributeValue, BillingMode, KeySchemaElement, KeyType,
    ScalarAttributeType,
};

#[tokio::test]
async fn put_then_get_returns_the_item() {
    let emulator = AwsEmulatorEmbedded::new(EmbeddedOptions::default());
    let config = aws_config::defaults(aws_config::BehaviorVersion::latest())
        .http_client(emulator.http_client())
        .region(aws_config::Region::new("us-east-1"))
        .credentials_provider(emulator.aws_credentials_provider())
        .load()
        .await;
    let ddb = aws_sdk_dynamodb::Client::new(&amp;config);

    ddb.create_table()
        .table_name("emulator-demo-table")
        .attribute_definitions(
            AttributeDefinition::builder()
                .attribute_name("id").attribute_type(ScalarAttributeType::S)
                .build().unwrap())
        .key_schema(
            KeySchemaElement::builder()
                .attribute_name("id").key_type(KeyType::Hash)
                .build().unwrap())
        .billing_mode(BillingMode::PayPerRequest)
        .send().await.unwrap();

    ddb.put_item()
        .table_name("emulator-demo-table")
        .item("id", AttributeValue::S("item-1".into()))
        .item("msg", AttributeValue::S("hi".into()))
        .send().await.unwrap();

    let got = ddb.get_item()
        .table_name("emulator-demo-table")
        .key("id", AttributeValue::S("item-1".into()))
        .send().await.unwrap();
    assert_eq!(got.item().unwrap().get("msg").unwrap().as_s().unwrap(), "hi");
}</code></pre> 
<p>When it runs as a local process, the emulator requires every request to be signed with Signature Version 4 (SigV4), the same way AWS does, and it exposes a <code>/__admin/health</code> endpoint on the same port so a script or a container can wait until it is ready before running tests. By default it also sends anonymous usage and error data, and you can turn it off.</p> 
<p><strong>How we measure fidelity</strong><br> An emulator is only useful if a test that passes against it would also pass against AWS, so we measure that directly with fidelity tests. A fidelity test is a short program that uses an AWS SDK to run a workflow, such as storing an object and then reading and deleting it, and asserts how AWS behaves. We verify each fidelity test against real AWS. A fidelity test passes only if the emulator matches AWS on the response to every call, including the status code, the body, and the exact error code and message, and on the resources and data that the workflow creates.</p> 
<p>With each release, we publish how many fidelity tests pass for each service, as k of n. For example, 40 of 50 means that 40 of the service’s 50 fidelity tests pass. The set of fidelity tests is public in the aws-emulator-evaluation-suite repository on GitHub, including the ones that don’t pass yet, so you can see what we verified and run the fidelity tests yourself. Read a score as a snapshot of a product that’s improving. When we add fidelity tests, a score can go down even while the emulator gets better.</p> 
<p>If the emulator doesn’t implement an operation yet, it returns HTTP 501 (Not Implemented), so your tests fail right away. If the emulator acts differently from AWS, you can tell us by opening an issue in the AWS Emulator repository on GitHub.</p> 
<p><strong>How the emulator is built</strong><br> AWS Emulator is built and maintained by agents from the AWS API models using <a href="https://aws.amazon.com/bedrock/agentcore/">Amazon Bedrock AgentCore</a> Runtime Instances, <a href="https://aws.amazon.com/codepipeline/">AWS CodePipeline</a>, and <a href="https://aws.amazon.com/codecommit/">AWS CodeCommit</a>, so it stays current with AWS as those models change.</p> 
<p>One group of agents looks for gaps, both by comparing emulator responses against real AWS and by statically comparing the emulator’s code against the published Smithy models, and files an issue for each gap it finds. Another group picks up an issue, writes tests, implements the behavior, and reviews the change for correctness, performance, and security. When the change is ready, it is pushed to a source repository, and that push triggers an AWS CodePipeline run that runs the fidelity tests before the change is published to the public GitHub repository.</p> 
<p><strong>How we keep it secure</strong><br> Because the code is written by agents, an independent security agent reviews changes adversarially, both while the fix is being made and again in the release pipeline as a final check before anything ships.</p> 
<p>Security of your own use remains a shared responsibility. We build the emulator to run safely on your machine: it listens only on your own computer by default and rejects requests that aren’t signed with its own keys. You decide where it runs, what data you put in it, and how you test before production. Don’t use the emulator to test whether your application is secure. It doesn’t evaluate <a href="https://aws.amazon.com/iam/">AWS Identity and Access Management (IAM)</a> policies and resource-based policies the way AWS does, so a request that AWS denies might succeed in the emulator. Keep real credentials out of the environment of your test jobs, and test your security settings and your whole application on AWS before you go to production.</p> 
<p><strong>Now available</strong><br> AWS Emulator is generally available today. It has no additional service fee. You pay only for AWS resources when you deploy on AWS. You can install it from RPM or Debian packages on Linux, run it in Docker on macOS and Windows, or build from source, and it works with the AWS SDKs and the AWS CLI once you set environment variables. At launch, it has some limits. It doesn’t evaluate IAM policies the way AWS does, and each emulator acts as a single account, with no cross-account or cross-Region behavior. How closely it matches AWS varies by service and feature. To see how well the emulator covers the services that you use, check the fidelity scores in the AWS Emulator documentation.</p>

Moving a Hive table to Apache Iceberg has typically meant weeks of engineering work. Last week, <a href="https://aws.amazon.com/s3/features/tables/">Amazon S3 Tables</a> turned that into three steps: start, sync as often as you need, complete. The source stays writable except for a few minutes at cutover. The same week, <a href="https://aws.amazon.com/dynamodb/">Amazon DynamoDB</a> started loading data from S3 into tables that already exist.</p> 
<p>The pattern I like is that neither one asks you to stop what’s running. That’s also the way to read the agent news this week. The new <a href="https://aws.amazon.com/bedrock/agentcore/">Amazon Bedrock AgentCore</a> Runtime is a single field on the runtime you already have, and Web Answer is a tool you attach to a gateway you already run. Now, let’s get into this week’s AWS news…</p> 
<p><span id="more-106158"></span></p> 
<p><strong>Headlines</strong><br> <a href="https://aws.amazon.com/blogs/machine-learning/the-new-agentcore-runtime-elastic-optimized-and-consistently-fast-starts/">The new AgentCore Runtime: elastic, optimized, and consistently fast starts</a> – If you run agents on AgentCore and haven’t tried the <a href="https://aws.amazon.com/about-aws/whats-new/2026/09/new-agentcore-runtime-generally-available/">new runtime</a> since it became generally available, it’s worth a look. It changes two things. First, memory: sessions start small, page in more on demand, and give memory back when it goes cold instead of holding the peak, so you pay for what your agent uses. Second, cold starts: AgentCore prepares your environment once, snapshots it, and restores the snapshot for every new instance. In the team’s tests, that kept P75 cold starts at about 2 seconds for images from 200 MB up to 2 GB, while the original runtime rose from roughly 5.4 seconds to nearly 30 seconds as images grew. The per-unit rate is higher, but you use far fewer GB-hours, so the team expects most agents to see a lower bill, though that isn’t guaranteed.</p> 
<p>To opt in, you set <code>platformVersion</code> to <code>V2</code> when you create or update a runtime. Create and update take several minutes while the snapshot is prepared, and your container must report healthy on <code>/ping</code> within 120 seconds, so report health only after initialization finishes. The docs cover <a href="https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-v2-optimize.html">how to optimize your agent for V2</a>. V2 is available in <a href="https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html#runtime-platform-versions">10 Regions</a>, and committed baseline pricing is coming soon.</p> 
<p><a href="https://aws.amazon.com/blogs/aws/amazon-s3-tables-now-offer-managed-migration-of-apache-hive-tables-to-apache-iceberg/">Amazon S3 Tables now offer managed migration of Apache Hive tables to Apache Iceberg</a> – You can now migrate Parquet tables registered in the <a href="https://aws.amazon.com/glue/">AWS Glue</a> Data Catalog into S3 Tables without building a pipeline or provisioning compute. S3 Tables validates the source and produces a compatibility report covering every object in scope. Each sync copies only what changed, so production keeps writing until cutover. Afterward you can query the table with <a href="https://aws.amazon.com/athena/">Amazon Athena</a>, <a href="https://aws.amazon.com/sagemaker/unified-studio/">Amazon SageMaker Unified Studio</a>, or any engine that speaks the Iceberg REST API. You pay only for the data copied, with no charge for the conversion, and objects in <a href="https://aws.amazon.com/s3/storage-classes/intelligent-tiering/">S3 Intelligent-Tiering</a> keep their tier. At launch it works within the same account and Region, in 10 Regions.</p> 
<p><strong>Last week’s launches</strong><br> Here are some launches and updates from this past week that caught my attention:</p> 
<p><a href="https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-dynamodb-now-supports-bulk-put-items/">Amazon DynamoDB now supports bulk put items</a> – You can now load line-delimited DynamoDB JSON or Amazon Ion files from <a href="https://aws.amazon.com/s3/">Amazon S3</a> into existing tables as a managed, asynchronous job. Each record can carry its own condition expression, so one file can mix plain, insert-only, and version-guarded writes. Writes use dedicated system capacity and cost less than the equivalent per-request writes. An Accelerated tier handles deadline-bound jobs. The <a href="https://aws.amazon.com/blogs/database/introducing-bulk-put-items-for-amazon-dynamodb-load-data-from-amazon-s3-into-existing-tables-at-scale/">Database blog post</a> gives illustrative Accelerated times of less than 1 hour for 100 million 1 KB items. One thing to know before you start: canceling doesn’t roll back items already written.</p> 
<p><a href="https://aws.amazon.com/about-aws/whats-new/2026/11/web-answer-amazon-bedrock/">Announcing Web Answer on Amazon Bedrock AgentCore</a> – You can now give an agent a single tool call that returns a synthesized, cited answer to a natural-language question, instead of building your own search, retrieval, and citation pipeline. Web Answer plans its own searches, runs several in parallel, and decides when it has enough evidence. You attach it as a target on AgentCore Gateway and call it over MCP, and you can limit it with domain include and deny lists and publish-date filters. It’s available in US East (N. Virginia). The <a href="https://aws.amazon.com/blogs/machine-learning/getting-started-with-web-answer-on-amazon-bedrock-agentcore/">getting started post</a> explains when to use it instead of Web Search, which returns ranked results for your own model to synthesize.</p> 
<p><a href="https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-queue-kafka-esm/">AWS Lambda now supports queues for Apache Kafka in self-managed Kafka event sources</a> – You can now process records from a single Kafka partition across many parallel <a href="https://aws.amazon.com/lambda/">AWS Lambda</a> invocations. Classic consumer groups cap parallelism at the partition count. Queue mode uses Kafka share groups and needs Kafka 4.2 or later with share groups enabled. It works with self-managed clusters and managed offerings such as Confluent Cloud. You give up ordering and get at-least-once delivery, so your functions need to be idempotent. The <a href="https://aws.amazon.com/blogs/compute/introducing-queue-consumption-mode-for-apache-kafka-in-aws-lambda/">Compute blog walkthrough</a> covers poller scaling and when to keep stream mode.</p> 
<p><a href="https://aws.amazon.com/about-aws/whats-new/2026/11/interconnect-last-mile-preview-equinix/">AWS announces AWS Interconnect – last mile preview with Equinix</a> – You can now set up a private, managed connection from Equinix’s network of 282 data centers to AWS without ordering cross-connects or configuring routers. Capacity is quad-redundant across two locations and four links, with BGP and VLANs configured for you, a 99.99% availability SLA, and MACsec by default. You pick a Region, bandwidth, and <a href="https://aws.amazon.com/directconnect/">AWS Direct Connect</a> gateway, then paste the activation key into Equinix Fabric. The preview covers the San Jose metro and, as of <a href="https://aws.amazon.com/about-aws/whats-new/2026/11/interconnect-last-mile-northern-virginia/">last Thursday</a>, Northern Virginia, with 1 Gbps connections at no charge.</p> 
<p><a href="https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-sbom-inventory/">AWS Security Hub now provides an SBOM inventory for your compute resources</a> – You can now see every software package installed across your organization’s <a href="https://aws.amazon.com/ec2/">Amazon EC2</a> instances, <a href="https://aws.amazon.com/ecr/">Amazon ECR</a> images, and Lambda functions in <a href="https://aws.amazon.com/security-hub/">AWS Security Hub</a>, with each package’s version and how many resources run it. That’s the list you want the next time a widely used library has a vulnerability. The inventory builds on the SBOMs that <a href="https://aws.amazon.com/inspector/">Amazon Inspector</a> already generates, so it fills in automatically wherever Inspector is enabled. It’s included in Security Hub Essentials at no additional cost.</p>

Migration works with Parquet tables in Amazon S3 that are registered in the <a href="https://aws.amazon.com/glue">AWS Glue</a> Data Catalog and allows you to upgrade your data lake with no pipelines to build or compute to provision, while production workloads keep running.</p> 
<p>Apache Iceberg has become the open standard for large analytics datasets. It lets you manage petabyte-scale tables with features like schema evolution, hidden partitioning, and time travel queries, while keeping your data open and queryable with any Iceberg-compatible engine. Amazon S3 Tables offer fully managed storage purpose-built to keep Iceberg tables performant and cost-effective as they grow, with features like automatic maintenance, optimization, replication, and <a href="https://aws.amazon.com/s3/storage-classes/intelligent-tiering/">S3 Intelligent-Tiering</a> built-in.</p> 
<p><strong><u>What is new</u></strong><br> Previously, migrating Apache Hive tables to Apache Iceberg could take weeks of engineering work to build and manage the required infrastructure. Converting data types and building rollback capabilities added operational complexity. Now, this is available as a managed, API-driven operation.</p> 
<p>S3 Tables handle the entire migration workflow, including data validation, compatibility checks, type conversions, file recompression, and compaction. Before copying any data, S3 Tables identify every source object in scope and generate a compatibility report. You can sync as many times as you need without stopping writes to your source table, except for a few minutes during cutover. Once you are ready, you can complete the migration, minimizing time that tables are offline.</p> 
<p>Compared to self-managed approaches, S3 Tables managed migrations are cost-effective because you pay only for the data copied, with no charge for the Hive-to-Iceberg conversion, and source objects in S3 Intelligent-Tiering stay in their current access tier.</p> 
<p><strong><u>A first look at the migration</u></strong><br> To migrate an AWS Glue Hive table, choose your destination table bucket in the <a href="https://console.aws.amazon.com/s3">S3 console</a>, then choose <strong>Create table from migration</strong>.</p>

<p><img loading="lazy" class="aligncenter size-full wp-image-106076" src="https://d2908q01vomqb2.cloudfront.net/da4b9237bacccdf19c0760cab7aec4a8359010b0/2026/10/20/2026-ECS-Gateway-architecture.png" alt="" width="1675" height="977"></p> 
<p>ECS Gateway introduces a clear separation of responsibilities between platform teams and application teams.</p> 
<ul> 
 <li><strong>Platform teams</strong> create and configure a gateway, defining organizational networking standards including subnets, security groups, TLS certificates, listener settings, and WAF web ACLs, in a single place. They then associate the gateway with one or more ECS clusters, making it available to services running on those clusters.</li> 
 <li><strong>Application teams</strong> opt their services in by adding a gateway connector parameter when creating or updating a service. ECS provisions the required per-service resources automatically: an ACM certificate, a unique DNS hostname, listener rules, target groups, and a service security group that permits inbound traffic only from the ALB. <p>ECS Gateway offers host-based routing using ALBs and enables up to 25 services to share a single ALB, optimizing infrastructure costs. <p><strong>ECS Gateway:Behind the scenes<br> </strong>A gateway can be associated with up to 10,000 clusters, and a single cluster supports up to five gateway associations. This many-to-many relationship gives platform teams the flexibility to share a gateway across environments or assign multiple gateways (for example, public and private) to a single cluster.</p> 
<p>Platform teams can control access by choosing which gateways to associate with which clusters. For additional control, use IAM policies to restrict who can deploy services to specific clusters.</p> 
<p>Application teams add the gateway connector to each service definition in <code>CreateService</code> or <code>UpdateService</code>. If you have an existing ECS service with its own load balancer, you can adopt ECS Gateway incrementally by calling <code>UpdateService</code> to add a gateway connector. <pre><code class="lang-bash">aws ecs create-service \ 
  --cluster my-cluster \ 
  --service my-api-service \

<p>At deployment time, Amazon ECS evaluates the gateways associated with the cluster and connects the service to every compatible gateway. A gateway is compatible when its access type matches the service’s connector filter, it is in the same VPC as the service, and it covers all Availability Zones used by the service’s configured subnets.</p> 
<p>For each connection, Amazon ECS assigns the service to an ALB with available capacity and provisions the per-service resources: an ACM certificate, a unique DNS hostname, a listener rule routing traffic for that hostname to the service target group, and a service security group allowing inbound traffic only from the ALB security group. If no existing ALB has capacity, ECS creates a new one (up to <code>maxAlbCount</code> referring to quota limit). <ul>

You can take a standard port-listening server built with Express, Hono, Fastify, Next.js, or any Node.js framework, deploy it with a single command, and Lambda automatically handles scaling, multi-region distribution, and active CPU billing. No adapters, no infrastructure to manage, and no framework lock-in.</p> 
<p>With this launch, AWS Lambda now offers three distinct form factors, each built on the same Firecracker isolation technology and designed for a different programming model.</p> 
<p><strong>Lambda Event Functions</strong> are what you already know as Lambda functions. They use the event-driven, single-concurrent handler model with wall-clock billing. We’re introducing the “Event Functions” name to highlight that programming model: your function receives an event, processes it, and returns a response. The event-driven programming model is ideal for event processing, queue consumers, and invocations triggered by other AWS services.</p> 
<p><strong>Lambda Web Functions</strong> use an HTTP-native programming model with multi-concurrent execution and active CPU billing. Your code listens on a port and handles standard HTTP requests. That programming model is ideal for web applications, API backends, and interactive HTTP workloads where multiple concurrent requests and I/O-heavy processing are the norm.</p> 
<p><strong>Lambda MicroVMs</strong> provide isolated, stateful sandbox environments with customer-managed lifecycles for running untrusted or user-generated code.</p> 
<p>The three complement each other. An application might use Event Functions for asynchronous backend processing, Web Functions for the user-facing API and server-side rendering layer, and MicroVMs for interactive code execution features, all within the same AWS account and sharing the same operational model.</p> 
<p><span style="text-decoration: underline"><strong>Why Web Functions<br> </strong></span>Modern web applications need to serve global audiences with fast, consistent response times while giving developers the freedom to use standard frameworks and iterate quickly. Building this today typically requires assembling multiple infrastructure components, configuring multi-region deployments, setting up latency-based routing, and tuning billing models to avoid paying for I/O wait. Developers often find themselves adapting their application code to fit a specific compute model rather than deploying the HTTP server they already have.</p> 
<p>Lambda Web Functions removes this complexity. Each execution environment handles multiple requests simultaneously (up to 128 concurrent requests per environment), which means a burst of incoming traffic can share warm environments instead of mapping each request to a new one. Web Functions meter the CPU time your code uses, so time spent waiting on a database query or an API call consumes little CPU. Memory is metered for as long as the execution environment exists. For I/O-heavy web workloads like server-side rendering, API backends, and AI inference endpoints streaming token responses, this can reduce compute costs.</p> 
<p><span style="text-decoration: underline"><strong>Let’s try it out<br> </strong></span>To get started, I wrote a simple Express.js server. This is the same code I run locally with <code>node index.js</code>, no Lambda-specific adapters or wrappers required.</p> 
<pre><code class="language-javascript">import express from 'express';

const app = express();
const [host, port] = process.env.AWS_LAMBDA_HTTP_ENDPOINT.split(':');

app.get('/', (req, res) =&gt; {
  res.json({ message: 'Hello from Lambda Web Functions!' });
});

app.listen(port, host, () =&gt; {
  console.log(`Server running on port ${port}`);
});
</code></pre> 
<p>The only difference from running locally is the <code>AWS_LAMBDA_HTTP_ENDPOINT</code> environment variable, which Lambda sets to the host and port your server must listen on. To run locally, set it yourself, for example <code>AWS_LAMBDA_HTTP_ENDPOINT=127.0.0.1:3000 node index.js</code>.</p> 
<p>With my code ready, I deployed using the <a href="https://aws.amazon.com/cli/">AWS Command Line Interface (AWS CLI)</a>:</p> 
<pre><code>aws lambda-web deploy --name my-web-app --code ./my-app
</code></pre> 
<p>One command. No prior resource setup. The CLI bundled my source, created the Web Function, published its first revision, attached a Web Function endpoint, and returned a live HTTPS URL in under a minute.</p> 
<p>A revision is an immutable snapshot of the code I deployed. The endpoint is the HTTPS URL that routes traffic to a revision, or splits traffic across revisions. Those are the resources I use to iterate and to control how traffic moves to new code.</p> 
<p>I tested it immediately:</p> 
<pre><code>$ curl https://&lt;domain-id&gt;.&lt;shard-id&gt;.lambda-web.us-east-1.on.aws/
{"message":"Hello from Lambda Web Functions!"}
</code></pre> 
<p>Next, I wanted my application to serve users in Europe and Asia with lower latency. I redeployed with multiple regions:</p> 
<pre><code>aws lambda-web deploy --name my-web-app --code ./my-app \
    --regions us-east-1,eu-west-1,ap-northeast-1
</code></pre> 
<p>Lambda Web Functions replicated my code to all three regions and configured latency-based routing automatically. Each request now routes to the Region with the lowest latency for the caller, on a best-effort basis, through one global URL (<code>&lt;domain-id&gt;.lambda-web.global.on.aws</code>).</p> 
<p>When I updated my code and ran the same deploy command again, the CLI detected the existing function, uploaded the new revision, and pointed the endpoint at it. Total turnaround from code change to live: seconds.</p> 
<p>For production workflows that require a more gradual rollout, I can shift traffic between revisions with a single API call:</p> 
<pre><code>aws lambda-web update-web-function-endpoint \
    --function-name my-web-app \
    --endpoint-name dev \
    --auto-deployment-mode Disabled \
    --revision-weights '[{"revisionId": "&lt;current-revision-id&gt;", "weight": 90}, {"revisionId": "&lt;new-revision-id&gt;", "weight": 10}]'
</code></pre> 
<p>This sends 90% of endpoint traffic to the current revision and 10% to the new one, giving me a canary deployment without additional tooling.</p> 
<p><span style="text-decoration: underline"><strong>Better together with Amazon CloudFront<br> </strong></span>For applications that combine static and dynamic content, Web Functions works well alongside <a href="https://aws.amazon.com/cloudfront/">Amazon CloudFront</a>. You can select a Web Function endpoint as the origin for your CloudFront distribution. Static assets are served from the cache while dynamic requests route to your Web Function, giving you CDN performance for static content with serverless compute for the dynamic parts.</p> 
<p>Web Functions improves the private-origin experience with CloudFront.&nbsp;With this launch, you attach CloudFront <a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-origin.html">origin access control (OAC)</a> to a Web Function endpoint instead. CloudFront signs requests to the origin, and the endpoint allows only your distribution to invoke it. You get the same private-origin pattern CloudFront already provides for <a href="https://aws.amazon.com/s3/">Amazon Simple Storage Service (Amazon S3)</a>, without exposing the endpoint or adding custom authorization to your app.</p> 
<p><span style="text-decoration: underline"><strong>Now available<br> </strong></span>AWS Lambda Web Functions is available today in US East (N. Virginia), US East (Ohio), US West (Oregon), Asia Pacific (Tokyo), and Europe (Ireland). Web Functions run Node.js 24 (nodejs24.x) on Arm64 at launch and support Amazon Virtual Private Cloud (VPC) connectivity, allowing your function to access resources that exist within a VPC.</p> 
<p>To get started, deploy your first Web Function in under a minute:</p> 
<pre><code>aws lambda-web deploy --name hello-world --hello-world
</code></pre>

Upgrade existing V2 tables or create new V3 tables with built-in compaction, maintenance, and engine compatibility. <p><a href="https://aws.amazon.com/s3/features/tables/">Amazon S3 Tables</a> now support all data types in the Apache Iceberg V3 specification. You can create V3 tables or upgrade existing V2 tables to take advantage of <a href="https://iceberg.apache.org/spec/#version-3-extended-types-and-capabilities">V3 features</a> like deletion vectors, row lineage, and new data types such as variant, nanosecond timestamps, unknown, geometry, and geography.</p> 
<p>Apache Iceberg has become the open standard for managing large analytics datasets. It lets you manage petabyte-scale tables with features like schema evolution, hidden partitioning, and time travel queries, while keeping your data in open Parquet files in data lakes on object storage like <a href="https://aws.amazon.com/s3/">Amazon S3</a>. Amazon S3 Tables offer storage purpose-built to keep Iceberg tables performant and cost-effective as they grow, with fully managed features like automatic compaction, maintenance, replication, and Intelligent-Tiering.</p> 
<p>Teams running analytics on Apache Iceberg V2 tables often hit the same limits as their data grows. A compliance request to delete 50,000 user records from a 2-billion-row table leaves behind positional delete files that slow queries until compaction runs. Semi-structured events land as JSON strings that every query has to parse. Geospatial coordinates and nanosecond-precision timestamps get encoded as strings or integers. Each workaround adds storage cost, query latency, and pipeline code. With V3, Iceberg solves these challenges by offering native support for semi-structured and geospatial data, faster row-level operations, and built-in row lineage for data governance.</p> 
<p>Starting today, Amazon S3 Tables support all V3 data types, including variant, nanosecond timestamps, geometry, geography, and unknown, along with deletion vectors and row lineage. This works well when a single team owns the architecture. As adoption grows across the organization, though, things get complicated. AWS best practices recommend a multi-account structure, which means each team runs in its own account. To route events between them, teams create multiple event buses connected through cross-account rules or bus-to-bus configurations. This workaround reintroduces the operational complexity that serverless architectures are meant to eliminate. Platform teams lose visibility into who is subscribing to which events, cross-account and bus-to-bus routing charges compound quickly, and teams that need capabilities like event ordering are forced to build complex workarounds or adopt entirely different technologies.</p> 
<p>Today, we are announcing an enhanced custom event bus in Amazon EventBridge, purpose-built for organizations scaling event-driven applications across teams and accounts. With the new enhanced custom event bus, you can deploy a single, centralized event bus shared across all AWS accounts in your organization, with ordering guarantees, a simplified Subscriber resource, and a new pricing model that delivers improved economics at scale and cost allocation for publishers and subscribers.</p> 
<p><span style="text-decoration: underline"><strong>Let’s try it out<br> </strong></span>To get started with an enhanced custom event bus, I navigated to the EventBridge console in the <a href="https://aws.amazon.com/console/">AWS Management Console</a> and opened the Create custom event bus page. I selected Custom event bus, the recommended option labeled New. The page also offered Custom event bus – classic, which continues to receive events and route them with rules and targets. Below the selection, EventBridge showed how the new bus works. One shared bus serves every team in the organization. Publishers send events, subscribers consume only what they need, and EventBridge handles ordering, retention, routing, and delivery.</p> 
<p><img loading="lazy" class="aligncenter size-large wp-image-105480" src="https://d2908q01vomqb2.cloudfront.net/da4b9237bacccdf19c0760cab7aec4a8359010b0/2026/09/01/image-01-1024x806.png" alt="" width="1024" height="806"></p> 
<p><em>The Create custom event bus page. Custom event bus is the recommended new option, with ordered delivery, filter patterns, event replay, and sharing across your AWS organization. Custom event bus – classic remains available for existing workloads.</em></p> 
<p>Next, I configured resource sharing. I turned on Enable event bus sharing and selected Allow sharing only within your organization. I chose AWS account ID as the principal type. I could also share with an organization, an organizational unit, or an <a href="https://aws.amazon.com/iam/">AWS Identity and Access Management (IAM)</a> role or user. Sharing uses <a href="https://aws.amazon.com/ram/">AWS Resource Access Manager (AWS RAM)</a>, so I did not have to set up cross-account permissions or bus-to-bus routing myself.</p> 
<p><img loading="lazy" class="aligncenter size-large wp-image-105481" src="https://d2908q01vomqb2.cloudfront.net/da4b9237bacccdf19c0760cab7aec4a8359010b0/2026/09/01/image-02-1024x463.png" alt="" width="1024" height="463"></p> 
<p><em>Resource sharing on the new custom event bus. I enabled sharing within my organization through AWS RAM and selected an AWS account as the principal, which is how teams publish and subscribe on the same bus without extra routing.</em></p> 
<p><span style="text-decoration: underline"><strong>Organization-wide sharing<br> </strong></span>With the new enhanced custom event bus, you can create a single event bus and share it across all AWS accounts in your organization. Platform teams deploy one bus and establish it as the central event backbone, eliminating the need to configure cross-account permissions or bus-to-bus routing. Application teams across your organization can publish and subscribe to events on the same bus without waiting for infrastructure provisioning.</p> 
<p>Publishers send events without needing to know which teams consume them, and subscribers create their own Subscriptions independently. Platform teams maintain visibility into all event flows and fine-grained control over who can publish and consume events. The new enhanced custom event bus has a default quota of 10,000 Subscribers per bus, and you can request a higher quota. That reduces the fragmentation that occurs when subscriber limits force you to split across multiple buses.</p> 
<p><span style="text-decoration: underline"><strong>Event ordering<br> </strong></span>Event-driven architectures work best when consumers are designed around asynchronous patterns, where the order of events does not matter. There are a few cases where order does matter. In a logistics application, driver location updates must arrive in sequence. Out-of-sequence events cause routing algorithms to make decisions based on stale data.</p> 
<p>The enhanced custom event bus supports both patterns on the same bus. Publishers can include an EventGroupId when sending events. EventBridge delivers events that share the same EventGroupId in sequence to Subscribers that chose ordered delivery. Other subscribers on that bus can receive the same events without ordering. You can keep events for each driver in the correct order without building complex workarounds, while the rest of your consumers stay fully asynchronous.</p> 
<p>To support ordered processing, the enhanced custom event bus includes synchronous invocation for targets like <a href="https://aws.amazon.com/lambda/">AWS Lambda</a>. Synchronous mode confirms successful processing before acknowledging the event, eliminating the common pattern of placing <a href="https://aws.amazon.com/sqs/">Amazon Simple Queue Service (Amazon SQS)</a> between an event bus and Lambda to ensure reliability.</p> 
<p><span style="text-decoration: underline"><strong>Subscriptions<br> </strong></span>The enhanced custom event bus introduces the Subscriber resource, which combines event filtering, target configuration, retry policies, and dead-letter destinations into a single, manageable unit. Today, achieving the same outcome with EventBridge requires configuring separate rules, targets, and retry settings across multiple resources. Subscribers simplify this by giving each consumer one resource that defines what events they want, where to deliver them, and how to handle failures.</p> 
<p>Subscribers also include variable start time options, making it easier for teams to onboard new consumers or replay events to recover from application errors or hydrate new applications.</p> 
<p><span style="text-decoration: underline"><strong>Event evaluation<br> </strong></span>Publishers can turn on content-based deduplication so EventBridge detects and drops retries of the same event from the payload itself. You do not have to generate and track a deduplication ID when a timeout or a partial failure sends the same event twice. EventBridge hashes the meaningful parts of the event and collapses matches that arrive within five minutes, which gives those retries exactly-once delivery semantics instead of EventBridge’s usual at-least-once model. If you already stamp your own idempotency token, keep using it. Content-based deduplication is for sources that cannot reliably identify the same event on a retry.</p> 
<p>Subscribers can use JSONata expressions to reshape an event before it reaches a target, extracting fields, renaming them, or computing new values when a downstream API expects a different shape. If you already produce Apache Avro or Protocol Buffers events, EventBridge can deserialize those payloads to JSON, allowing subscribers fine grained filtering and routing on the full event payload without having to consume, deserialize, and match or discard on their own.</p> 
<p><span style="text-decoration: underline"><strong>New pricing model<br> </strong></span>The enhanced custom event bus uses a new ingress and egress throughput pricing model. Publishers pay for events ingested, and subscribers pay for events delivered. This replaces the per-event model where cross-account and bus-to-bus routing charges compound in multi-bus architectures. For pricing details, visit the <a href="https://aws.amazon.com/eventbridge/pricing/">EventBridge pricing page</a>.</p> 
<p>Existing EventBridge custom event buses continue to work as they do today with no changes required. They now appear as Custom event bus – classic. The enhanced custom event bus is a new resource that you adopt at your own pace. In the console, it appears as Custom event bus.</p>
